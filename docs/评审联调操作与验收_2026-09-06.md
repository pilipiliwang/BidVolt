# 评审数据闭环：联调操作与验收

## 本轮范围与状态

- 临时联调页面：<http://127.0.0.1:4173/projects/207/review>。保留旧版布局，暂不迁移侧栏、评分布局和对话框。
- URL 中的 `207` 是项目 ID，页面上的 `44` 是项目名称，两者不要求相同。
- 本轮修复：首次评审不再要求前端已经拿到快照。评审接口会创建本次评审快照；仍要求成果已同步、生成任务结束、相关数据读取成功。
- 已核对前端调用和后端仓库 `adad445765128c7594c79dd0d989686732e74131` 的实现。下列示意字段不是项目 207 的真实返回值。
- **真实项目联调尚未验收完成。** 当前自动页面检查工具无法启动，独立 API 请求没有用户浏览器的登录状态，返回 401。这不表示用户浏览器的登录已失效。下面的真实操作应在已登录页面执行。
- 不自动确认建议、不自动上传测试材料、不修改正式成果；这些操作由用户决定。

## 一、先跑通“评审 → 结果读取”

### 1. 刷新页面，确认准备条件

1. 确认当前项目的生成任务已结束，成果目录能读取。
2. 刷新上述评审页面。等待加载完成，检查页面顶部是否有“部分项目数据加载失败”。如有，先点击“重试”，不要把下方空态当作没有评审记录。
3. 在右侧选择已启用的“成果完整性检查（内置）”。
4. 无历史快照不再阻止首次评审。按钮若仍禁用，应明确显示加载中、任务执行中、成果缺失或读取失败原因。

### 2. 发起一次评审

点击右侧 **“基于冻结快照运行评审”** 一次，等待提交结束；无需手动创建快照。

实际调用：`POST /api/v1/projects/207/evaluate`

请求体：`{"provider_id": <页面所选机制的真实编号>}`。不要照抄其他项目或测试示例的编号。

核对返回：本次 `run_id`、`score_id`、`snapshot_id`；失败时记录 HTTP 状态和业务错误原因。请求超时或结果不确定时，先读取评审记录，确认是否已创建，避免连续点击产生重复评审。

### 3. 核对页面与接口的同一组结果

前端提交后会重新读取项目数据：

| 读取接口 | 核对什么 | 页面应该显示什么 |
| --- | --- | --- |
| `GET /api/v1/projects/207/reviews` | 本次 `run_id` 是否存在、运行状态是否完成 | 实际评审状态，而不是继续显示未运行 |
| `GET /api/v1/projects/207/reviews/{run_id}` | `snapshot_id`、评审机制、`score.score_id` 与本次提交是否对应 | 本次冻结快照、评分摘要和建议上下文 |
| `GET /api/v1/projects/207/scores` | `score_id`、`review_run_id`、`total_score`、`improvable`、`missing_count`、`scale`、版本关联和过期状态 | 最新评分；版本或分值口径不一致时不能混用 |
| `GET /api/v1/projects/207/scores/{score_id}/items` | 每条 `item_id`、问题、建议、得分、可提升分、状态 | 中间建议列表中的对应条目 |

第一轮的通过条件是：**提交产生记录，读取接口返回同一组记录，页面呈现对应评分和条目。** HTTP 200、出现数字或按钮恢复可点击，单独都不代表闭环通过。

注意：当前评审页使用运行详情生成摘要，工作台评分卡使用最新评分接口。若两边不一致，应先对照 `run_id` / `score_id`，不要直接认为数据相同。

## 二、再跑“单项确认 → 实际处理 → 重审”

先选一条用户确实愿意处理的建议，**不要为了测试直接确认全部**。

### 4. 确认或不采纳一条建议

使用该建议的确认/不采纳按钮。

调用：`PUT /api/v1/projects/207/scores/{score_id}/items/{item_id}/confirm`

请求包括 `action: "confirm"` 或 `"reject"`，以及适用时的 `expected_version`。返回应明确是 `succeeded`、`conflict` 还是 `skipped`。完成后再次读取 items，确认条目状态已经保存，刷新页面也不丢。

**确认只表示采纳该建议，不代表文件已修改，也不应因为确认就声称实际标书得分提高。** 冲突时先刷新并核对版本，不重复提交旧条目。

### 5. 按建议实际补材料或修改成果

- 缺材料：使用“上传项目补充资料”，上传真实需要的材料，确认上传及解析完成。
- 需要改标书正文：回到成果工作台，打开对应正式文件修改并按既定方式保存；记录新文件版本。
- 修改“建议文字”只会保存建议说明，不会替用户修改标书文件。
- 本页底部旧对话框暂未整合完整日志；本轮不依赖它证明整改已执行。需要 Agent 协助时回到现有工作台核对其实际回复和成果。

### 6. 根据验证目标选择重新评审方式

| 目标 | 页面操作 / 接口 | 核对重点 |
| --- | --- | --- |
| 验证已确认建议的状态重审链路 | “重新评审已确认建议” → `POST /api/v1/projects/207/re-evaluate`，传 `item_ids` | 新 `run_id`、`score_id`、`new_item_ids`、`improved_count`，并重新读取明细 |
| 验证修改后的整份成果是否改善 | 再次运行评审 → `POST /api/v1/projects/207/evaluate` | 新评审实际引用了修改后的成果版本，而不只是旧结果重算 |

两种重审不是同一件事。更新后重新读取 reviews、run detail、scores、items，核对新旧 ID、条目变化、分值口径、成果版本。刷新页面后结果也应保留。

## 三、当前必须单独验证的后端能力

### 正式文件是否实际进入评分

当前生成工作台可展示正式 `artifact` 文件；已核对的后端评审服务读取的是 `Deliverable` 及其版本内容。**前端目录出现 12 个文件，不足以证明评审引擎已读取这 12 个正式文件。**

如果项目有正式文件，评审却提示缺少商务标/技术标/报价单，或评分版本关联为空，应保留对应结果，核对两类成果的关联，不能通过隐藏提示或补造分数解决。

### 分数上涨是否真的代表整改成功

已核对的后端局部重审实现仍有简化判断：对于已确认、动作类型为 `upload_material` 的条目，只要项目存在一条材料记录，就可能按满分处理，并未在这段判断中证明该材料就是本条所缺材料。

因此，**“确认 → 重审 → 涨分”目前只能证明接口状态流转，不能独立证明材料匹配和实际整改正确。** 不要为了测试随意上传无关文件；若出现涨分但缺失项未实际解决，应列为后端业务验收未通过。

当前内置评审还包含完整性规则和招标评分细则文本匹配。需要区分 `scale=builtin` 与 `scale=score_rules`；不同分值口径不能直接做前后涨分比较，更不等于真实专家评分。

## 四、数据没有出现时如何定位

| 实际现象 | 下一步核对 |
| --- | --- |
| 没有发出 evaluate 请求 | 检查按钮前置条件，不归因于后端没返回评分 |
| evaluate 返回错误 | 保存状态码和业务响应，不继续确认建议或重复运行 |
| evaluate 超时，但 reviews 已有新记录 | 读取这条记录，先确认结果，避免再次提交 |
| evaluate 成功，但 reviews 没有本次 run | 核对同一项目/企业及提交响应，属于记录落地或关联待核查 |
| reviews/detail/items 读取失败 | 重试读取，不能标记“尚未运行”或“暂无建议”作为事实结论 |
| 接口有评分/条目，但页面没有 | 对照 run/score/item ID，属于前端适配或展示待核查 |
| 提示缺少成果，但正式目录有文件 | 核对 artifact 与 Deliverable 评审输入关联 |
| 分数涨了，文件和材料实际没变 | 核对局部重审规则，不能判为整改闭环通过 |

## 五、联调记录怎么留

页面底部展开 **“API 联调测试框”**，查看接口是否触发和调用状态。需要核对具体返回数据时，在浏览器开发者工具的 Network 中筛选 `evaluate`、`reviews`、`scores`、`items`、`re-evaluate`，查看对应请求的 **Response**。

每轮记录：操作时间、项目 ID、成果版本、HTTP 状态、run/score/snapshot/item ID、页面展示结果、是否匹配。需要协助排查时提供相关响应或截图即可。

**不要复制 Authorization、Cookie、访问令牌或整份带认证信息的 HAR。** 响应中涉及完整项目文件内容和企业敏感资料时，也应仅提供本次问题所需字段。

建议先只完成第一轮“运行一次评审并显示结果”，确认具体数据后，再决定采纳哪一条建议进入第二轮。

## 六、本轮截图与评分输入核对（2026-09-06）

### 已经观察到什么

用户提供的项目 207 截图显示快照 247、综合分 100、可提升分 0，以及三条“商务标已生成 / 技术标已生成 / 报价单已生成”。这说明页面已经展示了一轮评审结果，但不能据此认定标书质量满分、建议确认或整改闭环完成。

### 后端代码已确认的逻辑

核对基线：后端仓库 main 提交 `adad445765128c7594c79dd0d989686732e74131`，主要涉及 `app/services/review_service.py`、`app/services/task_service.py`。

1. 招标解析有评分细则提取步骤，成功时保存 `req_type=score_rule`、评分标准及权重。模型未启用、没有可用文件/评分文本、调用或格式解析失败、条目缺少有效正数权重等路径，都可能没有生成有效细则。任务结果中的 `score_rules_extracted` 可用于核对。不能只凭“解析完成”认定细则已提取。
2. 评审只读取同一企业、同一项目且 `current=true` 的 `score_rule` 要求。没有细则时，退回三类成果完整性检查；三类齐全会归一化显示 100，口径为 `builtin`。
3. 有细则时，评审读取结构化成果版本的节点文本，以要求正文或评分标准前 10 个字符是否出现在成果中进行覆盖匹配，再按权重归一化。口径为 `score_rules`。这仍是简化规则，不能当作真实专家语义评标。
4. 最新评分应保存 `detail.score_rules.count` 等统计、`scale` 和成果版本关联。**当前有效细则是当前状态，评分统计是评审时记录；两者数量一致也不能证明版本一致。**

上述是代码路径核对；项目 207 的当前有效细则数量及这次评分原始统计，仍需在用户已登录页面读取。截图中的三条完整性结果与“本轮没有消费评分细则”相符，但尚不能据此指定根因是解析失败、数据时间差还是输入关联问题。
