# 企业资料列表接口需求审阅（待产品/后端确认）

> 日期：2026-09-03  
> 状态：仅供内部审阅，暂不提交 GitHub Issue  
> 范围：企业资料列表、自动归类、重命名、版本追溯与通知能力

## 背景与原则

企业资料页已按真实后端接口展示资料，不使用 Mock 数据，也不根据文件名伪造时间或压缩包关系。业务资料分类继续采用 `GET /enterprise/categories` 返回的固定分类；在后端补齐来源字段前，前端仅把扩展名明确为 ZIP/RAR/7Z 的原始压缩包放入独立的“源文件”展示视图，不把该视图冒充后端持久分类。

以下需求旨在补足列表查询与可追溯性契约。字段命名、枚举值和存储实现可由后端结合现有模型调整，但返回含义应稳定、可验证，并保证租户隔离。

## 1. 返回真实创建时间与更新时间

### 当前现状

`GET /enterprise/assets` 当前资料项缺少稳定的 `created_at`、`updated_at`。前端无法在列表中区分资料的真实上传时间和最近修改时间，也不应使用浏览器当前时间或数组顺序代替。

### 前端临时行为

前端兼容可选时间字段，并按以下顺序选择列表的“更新时间”：

1. `asset.updated_at`；
2. `asset.created_at`；
3. 用户打开详情后，使用最高 revision 的 `created_at`；
4. 均缺失或值无效时显示 `—`。

有效时间只展示到日期，格式为 `YYYY-MM-DD`。带时区的时间戳按浏览器所在时区换算；前端不会修补无效日期，也不会据此推断后端时间。

### 建议契约

建议 `GET /enterprise/assets` 的每个资料项至少补充：

```json
{
  "asset_id": 123,
  "created_at": "2026-09-03T08:30:00+08:00",
  "updated_at": "2026-09-03T10:15:00+08:00"
}
```

- 使用带时区的 ISO 8601 字符串；
- `created_at` 表示该企业资料记录首次建立时间；
- `updated_at` 表示会影响用户所见资料内容或元数据的最近更新时间；
- 若历史数据确实无法回填，可返回 `null`，不要返回占位字符串或当前请求时间；
- 详情接口与列表接口对同一资料应保持一致含义。

## 2. 提供服务端分页、检索、筛选与排序

### 当前现状

`GET /enterprise/assets` 当前返回扁平数组。资料量增加后，前端只能一次性下载全部记录，再在浏览器内搜索和分类筛选，无法准确表示后端数据总量，也不利于稳定加载。

### 前端临时行为

前端暂时消费后端返回的完整数组，在本地按名称和分类标签过滤。该行为只适合当前接口形态，不代表服务端已完成分页或全文检索。页面分类仍使用后端的真实 `category_id`，不会自行创造分类。

### 建议契约

建议列表接口支持以下查询能力：

| 参数 | 建议含义 |
| --- | --- |
| `page` | 页码，从 1 开始 |
| `size` | 每页数量，并设置合理上限 |
| `q` | 文件名及后端认可的可检索字段关键词 |
| `category_id` | 按真实企业分类筛选 |
| `source_kind` | 按资料来源类型筛选，例如普通上传、压缩包源文件或解包子文件 |
| `sort` | 明确允许的排序字段和升降序，例如 `-updated_at` |

建议响应使用项目其他分页接口一致的结构：

```json
{
  "items": [],
  "total": 1234,
  "page": 1,
  "size": 50
}
```

- `total` 应是应用全部筛选条件后的真实总数；
- 排序结果应稳定，同一时间值可再以 `asset_id` 作为稳定次序；
- 未传筛选参数时保持向后兼容；
- 参数非法时返回明确的 4xx 校验信息，不静默改写查询含义。

## 3. 持久表达压缩包源文件及解包关系

### 当前现状

上传接口可以返回当次压缩包的解包数量，但企业资料列表缺少持久、可查询的来源属性。页面刷新后，前端无法仅凭真实接口判断某项是原始压缩包、普通上传文件还是压缩包内的子文件，也无法可靠展示原始压缩包与解包子文件之间的关系。

### 前端临时行为

前端只在当前浏览器会话的上传回执中展示后端返回的导入、重复和失败数量；刷新后不保留该临时记录。列表会按 ZIP/RAR/7Z 扩展名建立只读“源文件”视图，并将这些原始压缩包从业务分类视图移出，但这只是当前 UI 的互斥展示规则：它不能证明文件来自压缩包处理流程，也不能还原解包子文件关系，更不会写回后端分类。

### 建议契约

后端可选择以下任一原则性方案：

1. 在资料项上持久返回 `source_kind`、`is_archive` 等来源属性；或
2. 提供一个固定、可查询的“源文件”分类/视图，用于定位原始压缩包。

无论采用哪种方案，都建议让原始压缩包与解包子文件关系可以从接口中明确还原。可参考但不限于以下字段：

```json
{
  "source_kind": "archive_entry",
  "is_archive": false,
  "source_archive_id": 456,
  "archive_path": "资质/许可证.pdf"
}
```

- 原始压缩包本身应有稳定 ID，且不应与某个解包子文件混淆；
- 子文件应能指向所属原始压缩包，并保留包内相对路径或等价的可追溯信息；
- 普通上传文件与解包文件应能通过明确字段区分，而不是依赖文件名猜测；
- 压缩包部分解包失败时，应保留可复查的真实状态和错误摘要；
- 删除、重复文件与重新解包后的关系语义需要保持一致，但具体生命周期规则由后端设计确认。

## 4. 完善基于内容的自动归类与确认闭环

### 当前现状

当前企业资料自动归类只依据文件名关键词。上传 ZIP 后，包内条目又以文件 basename 进入归类流程，因此 `image030.png`、`inline265.jpeg` 等不含业务关键词的文件会稳定落入“其他”。后续生成的图片描述不会反向更新分类；重新调用归类接口也只是再次执行同一套文件名规则。

后端目前会把资料或归类任务标记为“待确认”，但没有确认归类结果的接口；现有分类修改接口只更新目录，不完成确认状态闭环。

### 前端临时行为

前端继续以 `GET /enterprise/categories` 和资料项返回的 `category_id` 为准，不根据识别文案自行伪造分类，也不把重新执行同一规则包装成更智能的内容归类。页面不再向普通用户突出没有可操作闭环的“待复核”提示。

### 建议原则

- 自动归类应能使用正文、OCR/图片描述、包内路径及父压缩包上下文，而不只依赖 basename；
- 归类结果应返回可解释的置信度或依据，并允许用户通过真实接口修正；
- 若保留“待确认”状态，需要提供确认接口并明确状态流转；
- 分类修正后，资料列表、详情和后续投标任务应读取同一结果；
- 现有固定分类和后端允许创建自定义分类的关系，需要形成稳定契约，前端仍以后端返回目录为准。

## 5. 提供资料重命名接口

### 当前现状

在线 OpenAPI 与后端路由均未提供企业资料名称更新接口。现有 `PATCH /enterprise/assets/{asset_id}/category` 只能修改分类；资料详情中的 `name` 和下载时使用的原文件名无法由前端真实保存修改。因此当前不实现“双击改名”的假交互。

### 建议原则

- 提供企业资料名称更新能力，并返回保存后的权威资料对象；
- 明确修改的是资料展示名、原文件下载名，还是两者；
- 保留原始文件名和操作者、时间等审计信息；
- 处理重名、非法字符、长度、并发更新和租户隔离；
- 更新后列表、详情、搜索与下载行为保持一致。

## 6. 明确版本记录与资料关键信息的语义

### 当前现状

`GET /enterprise/assets/{asset_id}/revisions` 真实存在，但目前只返回原文件 revision 列表；后端没有单版本详情或追加/替换版本接口，现有流程通常只有首次上传生成的第 1 版。因此它目前更接近原文件哈希与来源追溯，而不是完整版本管理。

资料 `facts` 是抽取出的结构化键值，用于复用证号、主体、日期等关键信息，并非文件正文。当前 fact 状态在模型、人工纠正接口和任务写入逻辑之间存在枚举语义不一致，前端无法可靠解释“已确认/已纠正”。

### 前端临时行为

- “版本记录”只展示后端真实返回的原文件版本，不暗示可以恢复或编辑历史版本；
- “结构化字段”改为用户可理解的“资料关键信息”；
- 删除“识别结果来自后端”等实现说明，仅保留对用户有帮助的核对提示；
- 不依据冲突的状态值向用户展示确定性的确认结论。

### 建议原则

- 明确资料版本的创建时机、追加方式、单版本读取/预览与审计语义；
- 统一 fact 状态枚举及其流转，保证列表、详情、纠正记录含义一致；
- 将原文件版本与字段纠正版本明确区分，避免前端混为一套历史。

## 7. 通知能力

当前后端没有通知列表、未读数或标记已读接口。任务状态和 SSE 只能表达具体任务进度，不能等价支持全局通知中心，因此前端移除无行为的通知铃铛。若未来需要恢复，应先由后端提供真实通知契约。

## 审阅结论

前端当前可以兼容时间字段、提供客户端分页，并以互斥的“源文件”视图改善浏览体验；详情弹框也只展示接口真实提供的预览、关键信息与原文件版本。服务端若不补齐上述契约，真实时间、海量资料检索、压缩包来源追溯、内容归类、重命名以及状态确认仍然受限。建议后端确认最终契约后，由前端继续接入；在此之前不提交 Issue，也不把临时展示规则描述为后端能力。
